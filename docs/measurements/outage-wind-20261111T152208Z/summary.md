## Per edge, over the whole run

`sent` is `otelcol_exporter_sent_metric_points` — points that crossed the link. `dropped` is
`enqueue_failed_metric_points`, the one that would mean a point never made it into the queue.
`retries` is `send_failed_metric_points`, which counts failed *attempts*, so a large number
during an outage is the retry loop working, not loss.

## The end-to-end check, and what a restart does to it

The hub's `otelcol_receiver_accepted_metric_points` is aggregate across all five edges and
carries no sender attribute, so the cross-check is *sum of every edge's sent delta* against
*the hub's accepted delta*, both restart-aware: **361471 sent, 459150 accepted,**
0 refused.

## Verdict

- **Nothing was lost.** No edge failed to enqueue a point; wind's queue reached
  1431 batches and drained back to 0; the hub refused nothing.
- **Nothing was rewritten.** The batches carry their original timestamps, so the store sees
  the outage as a *late* history rather than as a gap — which is what makes an hours-long
  link failure survivable at a site with no local historian.

## Disk growth

Peak 32841 KiB at 1431 batches — about 22.9 KiB per batch.

Per hour, from the run: see the `samples.csv` column `disk_kib`, which is Docker's own volume
size (KiB) sampled every minute. Capacity is 5 000 batches per exporter, so the queue is the
binding limit long before the disk is: at this rate a **full** queue would be roughly
336 MiB, and the file-backed queue is not fsynced
per batch — the point is that it is measured, not that it is small.
